Use the self-hosted `bitrouter/auto` selector when a bound policy should select the model for each request. Connect usable inference sources first, initialize the policy binding, then inspect the serving route and review evidence before publishing policy changes.

[Strategies](/docs/routing/strategies) explains selector resolution, candidate eligibility, and named variants. [Configuration (YAML)](/docs/routing/configuration) covers file discovery, validation, and reload. Automatic model selection remains separate from [Model Fallbacks](/docs/models-routing/model-fallback) after a retryable failure.

Use [Routing Traces](/docs/routing/routing-traces) to follow the router's decisions, serving models, and upstream attempts across the available workflow trajectory.

## Local and Cloud pricing

Self-hosting the OSS router has no BitRouter fee. Cloud Auto Routing and Elastic Inference share **$0.01 per million processed tokens — early access pricing**. Actual input + output tokens are counted once per request, including when Auto Routing selects Elastic Inference. Your provider or supplier charges for model inference separately. Enterprise terms are custom. See [pricing](/pricing).

## Policy tiers and evidence

Initialize a binding with usable models for its tiers. An unmatched fingerprint uses the configured default tier. In alpha.33, legacy request-time adequacy learning is disabled. [Workload Optimization](/docs/routing/workload-optimization#let-evidence-improve-the-policy) explains how to use admitted evidence to update the policy.

Context-view selection has separate runtime rules. The model policy lock does not configure an external harness's history, and this page does not introduce unsupported context-strategy YAML. See [Context Routing](/docs/routing/context-routing).

## Initialize a policy binding

`bitrouter/auto` uses the routing policy bound to the named `auto` router. An explicit logical model id selects that model while retaining eligible provider fallback; a provider-qualified id pins one provider. Automatic selection and failure-driven fallback are separate decisions.

For a local deployment, initialize the policy binding with two active `provider:model` routes available in your deployment:

```bash
bro policy init auto --router auto \
  --strong openai:openai/gpt-5.6-sol \
  --economy moonshotai:moonshotai/kimi-k2.7-code
bro policy check
bro route bitrouter/auto
```

The initializer writes `policy-lock.yaml` and updates `bitrouter.yaml` while preserving the configured policy mode. The local endpoint fails visibly if the binding is missing. Hosted callers use a catalog model ID or an enabled workspace routing preset addressed as `@<name>`. A hosted preset can supply its own model or accept one as `@<name>/<base-model>`.

Use the selector in an API request or native harness launch:

```bash
bro claude --model bitrouter/auto
bro codex --model bitrouter/auto
```

[Responses API](/docs/usage/responses-api) shows a routed generation request. Inspect the actual serving model with [Request receipts](/docs/cli/request-receipts); a selector preview does not prove which fallback ultimately served the call.

## Override one call

Use an explicit selector when the caller should choose the model for one invocation:

```bash
bro claude --model openai/gpt-5.4
bro codex --model openai:openai/gpt-5.4
```

An explicit logical id retains eligible provider alternatives. A provider-qualified id also pins the provider. See [Virtual Models](/docs/models-routing/virtual-models#model-selector-forms) for selector resolution and named endpoint definitions.

## Verify and apply the policy

```bash
bro config validate -c bitrouter.yaml
bro route bitrouter/auto -c bitrouter.yaml
bro policy check -c bitrouter.yaml
bro requests --limit 25
```

Use `policy check` to inspect the binding used by `bitrouter/auto`. For other selectors and candidate constraints, use [Strategies](/docs/routing/strategies). Route previews do not send inference or establish task quality; settled [Request receipts](/docs/cli/request-receipts) show what actually served a call. Apply configuration changes through [Configuration (YAML)](/docs/routing/configuration#apply-and-review-changes), and publish policy candidates through the [review workflow](/docs/routing/workload-optimization#review-and-publish-a-change).
