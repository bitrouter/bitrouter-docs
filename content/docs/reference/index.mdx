Call BitRouter through one of its supported [inference protocols](/docs/usage/responses-api). New integrations can start with Responses; existing clients can retain a supported request format.

<Callout type="warn">
The BitRouter API is in early beta. Pin your integration to the behavior you test and review release notes before upgrading.
</Callout>

## Choose a deployment

| Deployment | HTTP origin | OpenAI-compatible SDK base URL | Caller credential |
| --- | --- | --- | --- |
| Cloud | `https://api.bitrouter.ai` | `https://api.bitrouter.ai/v1` | Cloud API key or supported bearer credential |
| Local default | `http://127.0.0.1:4356` | `http://127.0.0.1:4356/v1` | Local virtual key when authentication is enabled |

Cloud can be called directly from an application without running a local daemon. Local operation requires a running router and configured inference sources. [Authentication](/docs/reference/authentication) explains the credential boundaries.

## Get a Cloud credential

[Create a scoped Cloud API key](/docs/cli/cloud-management#create-an-api-key) with `inference:invoke`. Follow the CLI sign-in instructions on that page if you have not authenticated yet, then set the issued key in your application environment:

```bash
export BITROUTER_API_KEY='paste-your-cloud-key-here'
```

## Model discovery

Use [GET /v1/models](/docs/reference/discovery/listModels) to discover catalog model IDs and the supported provider, model, and modality filters. A catalog entry does not grant account access or guarantee capacity for a request.

[Virtual Models](/docs/models-routing/virtual-models#model-selector-forms) explains logical model IDs, explicit provider routes, and locally configured names. The separate [model market](/models) is an illustrative Elastic Inference preview, not the callable-model catalog.

## First Cloud request

Choose a catalog model your account can access. The following request uses an example model ID; replace it with your selected ID or an enabled workspace routing preset:

```bash
curl https://api.bitrouter.ai/v1/responses \
  -H "Authorization: Bearer $BITROUTER_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"anthropic/claude-haiku-4.5","input":"Hello!"}'
```

Inspect the response status and `output` items. Authentication success or catalog presence alone does not guarantee a completed model request. [Inference APIs](/docs/usage/responses-api#responses) explains responses, streaming, tools, and continuation; [Endpoint Reference](/docs/reference/openai-responses/createResponse) owns the hosted request and response schema.

## Python client

Use the [OpenAI Python SDK](https://developers.openai.com/api/reference/python) as a compatible client for the Responses request above:

```bash
python -m pip install openai
```

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://api.bitrouter.ai/v1",
    api_key=os.environ["BITROUTER_API_KEY"],
)
response = client.responses.create(
    model="anthropic/claude-haiku-4.5",
    input="Hello!",
)
print(response.output_text)
```

The SDK uses your BitRouter Cloud key and sends this request to BitRouter.
Compatibility depends on the fields and capabilities supported by the [BitRouter endpoint contract](/docs/reference/openai-responses/createResponse).

## Local router

Follow [CLI Getting Started](/docs/cli/getting-started) to configure and start the daemon. Choose a selector listed by `bro models` for that configuration. Use its local origin and a local virtual key when authentication is enabled.

The [Inference APIs examples](/docs/usage/responses-api#choose-an-endpoint-and-model) show a local request. `bitrouter/auto` requires a local policy binding configured through [Auto Router](/docs/routing/auto-router); Cloud uses catalog IDs or enabled workspace presets.
