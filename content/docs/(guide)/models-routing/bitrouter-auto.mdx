---
title: bitrouter/auto
description: Use a self-hosted model id to route requests through a policy you own, inspect, and can override.
---

`bitrouter/auto` is a self-hosted model id for policy-driven routing. Keep it in your local application or agent configuration while BitRouter resolves each request through the policy bound to the named `auto` router.

An explicit model id still bypasses that policy. Use `bitrouter/auto` for calls the router should choose; use a logical `provider/model` id when a call must stay on a model you selected.

## Before you send a request

The self-hosted endpoint needs an `auto` router with a routing policy bound to it. BitRouter fails visibly when that binding is missing rather than silently guessing a model.

| Deployment | What you need |
| --- | --- |
| BitRouter Cloud | A Cloud credential and a catalog model ID, or an enabled workspace routing preset addressed as `@<name>` |
| Self-hosted | A running `bro` proxy, at least one usable model route, and a local policy bound to the `auto` router |

Start with the [Quickstart](/docs/overview/quickstart) if the endpoint is not running yet. Use `bro models` to see the logical model ids currently available.

## Send the first request

The model id works anywhere BitRouter accepts a model selector. For an OpenAI-compatible local request:

```bash
curl http://127.0.0.1:4356/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "bitrouter/auto",
    "messages": [{"role": "user", "content": "Summarize this change."}]
  }'
```

For the hosted endpoint, use `https://api.bitrouter.ai/v1` and authenticate with your Cloud credential. Use a catalog model ID or an enabled workspace preset such as `@<name>`; `@auto` works only if the workspace has an enabled preset named `auto`. A hosted preset may specify its own model, or you can supply one as `@<name>/<base-model>`. The local `bitrouter/auto` selector is not a hosted routing preset.

## Use it from a coding agent

Pass the model when BitRouter launches the harness:

```bash
bro code codex --model bitrouter/auto
bro claude --model bitrouter/auto
bro codex --model bitrouter/auto
```

For a harness that connects directly to the local proxy, set its model to `bitrouter/auto`. For Cloud, use a catalog model ID or an enabled workspace preset instead. The [Coding agents](/docs/integration/coding-agents) page documents the environment variables and authentication boundary for each supported harness.

## Create the local binding

`bro policy init` creates a routing-policy lock and binds it to a named router. Both tiers must use configured, active `provider:model` routes. The following example assumes the OpenAI and Moonshot providers and those models are available; check `bro models` and combine an available provider and model as `provider:model` for your own setup:

```bash
bro policy init auto --router auto \
  --strong openai:openai/gpt-5.6-sol \
  --economy moonshotai:moonshotai/kimi-k2.7-code
```

The command writes `policy-lock.yaml` and updates `bitrouter.yaml` with the binding while preserving the configured policy mode. Keep both files in version control. The initializer validates the model identities and seeds the policy invariants.

Check the artifacts before starting traffic:

```bash
bro policy check
bro policy status
bro route bitrouter/auto
```

`bro route` verifies selector resolution and the configured candidate chain. The settled request record is the authority for the model and provider that actually served a request.

## Inspect what served

For a self-hosted router:

```bash
bro requests --limit 25
```

For BitRouter Cloud:

```bash
bro cloud requests --limit 25
```

The receipt distinguishes the requested selector from the resolved model and serving provider. Retries and fallback attempts are separate telemetry hops; the settled route is not inferred from response text.

Use [Telemetry](/docs/config/telemetry) when you need traces, metrics, sampling, or exporter configuration. Use [Evaluations](/docs/models-routing/evaluations) when you need to decide whether the result met an objective.

## Override one call

You do not need a second endpoint to opt out of automatic selection:

| Selector | Effect |
| --- | --- |
| `bitrouter/auto` | Resolve through the policy bound to `auto` |
| `openai/gpt-5.4` | Request one logical model while preserving eligible provider fallback |
| `openai:openai/gpt-5.4` | Pin one configured provider and model |

Prefer the slash form for a deliberate model override. Use the colon form only when the provider account itself is part of the decision. See [Model routing](/docs/models-routing/models#model-selector-forms) for the complete resolution order.

## Let evidence improve the policy

Use [Routing policy](/docs/models-routing/policy) to compile, review, and publish a candidate. Use [Evaluations](/docs/models-routing/evaluations) for objective-scored evidence and the separately authorized optimizer workflow.

## Diagnose a request

| Symptom | Check |
| --- | --- |
| The `auto` policy is not bound | `bro policy status`, then initialize or repair the `auto` binding |
| No model is eligible | `bro models`, provider credentials, and policy tier model ids |
| The candidate chain is unexpected | `bro route bitrouter/auto` and [Model routing](/docs/models-routing/models) |
| A call did not use the policy | Confirm its requested model was `bitrouter/auto`, not an explicit model id |
| The serving route is unclear | Inspect the settled local or Cloud request receipt |
| Traces are missing | Check `bro observe status` and [Telemetry](/docs/config/telemetry) |
