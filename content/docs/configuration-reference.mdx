## Version and scope

The field tables are generated from the **1.0.0-alpha.33 configuration schema**, pinned to [BitRouter source `54c822a34d4d`](https://github.com/bitrouter/bitrouter/blob/54c822a34d4dbfd75d484ca35e108b497048efef/dist/schema/bitrouter.config.schema.json) (source commit dated 2026-10-16). This is a source/schema snapshot, not a claim that every installed binary supports these fields. Check `bro --version` and validate with the binary that will run the file. The [CLI reference](/docs/cli/reference) has its own captured command version.

[Download the pinned JSON Schema](/schemas/bitrouter.config.schema.json) for an editor or offline validation. The schema describes file structure; runtime validation, credentials, model capabilities, and policy bindings can impose additional requirements.

```yaml
# yaml-language-server: $schema=https://bitrouter.ai/schemas/bitrouter.config.schema.json
```

This site URL serves the snapshot documented here and can change with a docs update. Save the schema locally, or use the commit-pinned source link above, when matching an older deployment.

**Reading the tables:** `Required` applies to the containing object or tagged alternative. `Not declared` means the schema does not publish a default; it does not mean the field is required, disabled, or empty. A schema `null` default is distinct from an inherited or resolved runtime value. Map keys such as provider and agent ids are user-defined; follow the linked type to inspect each value's fields. Types and enum values reflect the pinned schema.

<Callout type="warning">
Schema defaults and onboarding defaults differ. The schema declares `server.listen: "0.0.0.0:4356"` and `server.skip_auth: false`. The local configuration written by `bro init` uses `127.0.0.1:4356` with `skip_auth: true`. Inspect your actual file before assuming a listener or authentication mode. Neither setting grants access to the separate control or task APIs.
</Callout>

## Environment references

| Input | Meaning |
| --- | --- |
| `-c/--config PATH` | Select an explicit configuration file for commands that accept it. A missing explicit file is an error. |
| `BITROUTER_HOME` | Configuration discovery and runtime home override. A project-local file takes precedence during file discovery. See the [complete discovery order](/docs/routing/configuration#find-the-active-configuration). |
| `${NAME}` inside YAML | Substitute the named environment variable; an undefined variable is a configuration load error. |
| `${NAME:-fallback}` inside YAML | Use the fallback when the variable is unavailable. Substitution in YAML comments is ignored. |
| `RUST_LOG` | Overrides `server.log_level`. The log filter is resolved at process startup. |
| A field named `token_env` | Names the variable containing a dedicated credential; enter the variable's name in YAML, not the token itself. Consult that field's description. |

Provider-specific automatic credential discovery is covered by [BYOK & Subscriptions](/docs/models-routing/byok-subscriptions#built-in-providers-with-your-own-key). Provider credentials, a client's BitRouter virtual key, and a dedicated control/task API token serve different authentication hops. A YAML `${NAME}` reference can use a variable name you choose; it does not itself register a new automatic provider environment variable.

These file-loading conventions are source-checked against the pinned [configuration loader](https://github.com/bitrouter/bitrouter/blob/54c822a34d4dbfd75d484ca35e108b497048efef/crates/bitrouter-sdk/src/config/mod.rs) and [application paths](https://github.com/bitrouter/bitrouter/blob/54c822a34d4dbfd75d484ca35e108b497048efef/apps/bitrouter/src/paths.rs).

## Reload and restart

The schema does not encode hot-reload support. The pinned [reload implementation](https://github.com/bitrouter/bitrouter/blob/54c822a34d4dbfd75d484ca35e108b497048efef/apps/bitrouter/src/reload.rs) classifies changes against the daemon's startup configuration and live consumers.

| Change | Activation boundary |
| --- | --- |
| Listener, control socket, log filter, authentication mode, or known-pricing admission under `server` | Restart required. |
| Named `routers`, compiled `checkers`, `agents`, MCP connections/aggregation, or plugin configuration | Restart required in this source snapshot. |
| Database URL, native decision backend, recording/retention settings, or continuation retention | Restart required. |
| Provider routing and credentials | Some changes reload, but provider adapter membership, pricing, and other startup-owned consumers can require restart. Do not treat the entire `providers` map as hot-reloadable. |
| Any unclassified or unsupported change | Inspect the daemon's result; do not infer successful activation from a saved file or a valid schema. |

Local `bro reload` can forward provider environment values from the invoking shell. SIGHUP cannot carry newly exported shell values; remote-context reload uses server-owned files without forwarding the client's environment. Check the reload result and `bro status` (`config_state` when available) before relying on new settings. Older daemons may not expose this evidence. See [apply and review changes](/docs/routing/configuration#apply-and-review-changes) for the workflow.

## Server and connections

### Server Config

HTTP server settings.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `control_socket` | `string` | No | `"./bitrouter.sock"` |
| `listen` | `string` | No | `"0.0.0.0:4356"` |
| `log_level` | `string` | No | `"info"` |
| `require_known_pricing` | `boolean` | No | `false` |
| `skip_auth` | `boolean` | No | `false` |

- `control_socket` — Unix control socket path.
- `listen` — `host:port` to listen on.
- `log_level` — Log filter for the daemon, in `tracing-subscriber` `EnvFilter` syntax — a bare level (`debug`) or a per-target list (`info,bitrouter=debug`). `RUST_LOG` overrides this when set, following the Rust convention. The filter is resolved once at startup, so changing it needs a restart — `bro reload` will not pick it up. Applies to `bro serve` (and therefore `start`); other subcommands install their subscriber before any config is read and honour `RUST_LOG` only.
- `require_known_pricing` — Deny dispatch when any routed tariff cannot guarantee complete known-price coverage. Decisions caching remains unverified and fails this admission.
- `skip_auth` — SDK-level flag: when `true`, credential-less requests are admitted with a synthesised local caller. Code default is **`false`** — only the config file produced by `bro init` writes `true`.

### Upstream Config

Outbound / upstream HTTP settings — the client BitRouter uses to call providers. Distinct from `ServerConfig`, which is the inbound listen socket. Currently just `timeouts`; grouped under `upstream:` so future outbound knobs have a home.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `fallback_backoff_ms` | Array of `integer` (`format`: `uint64`; `minimum`: `0`) | No | `[]` |
| `timeouts` | [Timeout Config](#timeout-config) | No | Not declared |

- `fallback_backoff_ms` — Optional delay schedule before advancing through a retryable fallback chain, in milliseconds. The first value applies before the second candidate, the second before the third, and the last value repeats when the chain is longer than the schedule. Empty (the default) preserves immediate fallback.
- `timeouts` — Global upstream timeout defaults. A provider may override any field under `providers.<id>.timeouts:`.

### Database Config

Database connection settings.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `url` | `string` | No | `"sqlite://./bitrouter.db"` |

- `url` — Connection URL (e.g. `sqlite://./bitrouter.db`).

### Control Config

Scoped operator administration API settings. The control API is deliberately separate from the inference listener and the local control socket. It is disabled by default, may bind only to a loopback address, and authenticates named credentials when configured. Otherwise `BITROUTER_CONTROL_TOKEN` grants read-only access. `ServerConfig::skip_auth` never applies to it.

Unknown fields are rejected in this object.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `credentials` | Array of [Control Credential Config](#control-credential-config) | No | Not declared |
| `enabled` | `boolean` | No | `false` |
| `listen` | `string` | No | `"127.0.0.1:4358"` |

- `credentials` — Explicit operator credentials. Empty keeps the legacy read-only token.
- `enabled` — Whether to start the HTTP control listener.
- `listen` — Loopback `host:port` to listen on.

### Agent Api Config

Privileged HTTP access to the BRO task service. The app validates a loopback listener, nonempty token environment variable, and workspace allowlist before binding; `server.skip_auth` never grants this authority.

Unknown fields are rejected in this object.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `enabled` | `boolean` | No | `false` |
| `listen` | `string` | No | `"127.0.0.1:4359"` |
| `token_env` | `string` | No | `""` |
| `workspaces` | Array of `string` | No | `[]` |

- `enabled` — Whether to bind the task HTTP listener.
- `listen` — Loopback host and port, distinct from inference and control.
- `token_env` — Environment variable containing the dedicated task bearer token.
- `workspaces` — Exact server-owned workspace paths admitted for task submission.

### Timeout Config

Upstream HTTP timeout knobs, in seconds. Every field is optional; an unset field inherits the level above — a provider override inherits the resolved global value, and an unset global inherits the built-in default (`HttpTimeouts::default`). `total_secs` is opt-in at every level: unset ⇒ no overall wall-clock cap (the right default for long agentic streams). Used both as the top-level `upstream.timeouts` block and as the per-provider `providers.<id>.timeouts` override; timeouts are **not** inherited via a provider's `derives:` chain.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `connect_secs` | `integer` or `null` | No | `null` |
| `pool_idle_secs` | `integer` or `null` | No | `null` |
| `read_secs` | `integer` or `null` | No | `null` |
| `tcp_keepalive_secs` | `integer` or `null` | No | `null` |
| `total_secs` | `integer` or `null` | No | `null` |

- `connect_secs` — TCP connect timeout, seconds. `format`: `uint64`; `minimum`: `0`
- `pool_idle_secs` — Idle pooled-connection eviction, seconds. `format`: `uint64`; `minimum`: `0`
- `read_secs` — Idle (per-read) timeout, seconds — fires when the upstream sends no bytes for this long, including mid-stream. The effective stream-idle guard. `format`: `uint64`; `minimum`: `0`
- `tcp_keepalive_secs` — TCP keepalive probe interval, seconds. `format`: `uint64`; `minimum`: `0`
- `total_secs` — Overall wall-clock cap for the entire request/stream, seconds. Opt-in: unset ⇒ no cap. Setting it bounds total stream duration, so keep it generous for reasoning / agentic providers. `format`: `uint64`; `minimum`: `0`

### Control Credential Config

A token reference only; configuration never stores the bearer value.

Unknown fields are rejected in this object.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `id` | `string` | Yes | Not declared |
| `scopes` | Array of [Control Scope](#control-scope) | Yes | Not declared |
| `token_env` | `string` | Yes | Not declared |

- `id` — Non-secret operator identifier used for ownership and audit events.
- `scopes` — Explicit management authority, unrelated to inference authentication.
- `token_env` — Host environment variable that contains this credential's bearer token.

### Control Scope

Authority granted by a host operator, independently of inference credentials.

Exactly one of the following shapes:

**`Alternative 1`**

Host-wide operational inspection, including usage and policy metadata.

Accepted value: `"control:read"`.

**`Alternative 2`**

Reload server-owned configuration; requires the read grant as well.

Accepted value: `"control:reload"`.

## Providers and models

### Provider Config

One upstream provider entry — registry-style. `Debug` redacts `api_key` (v0 audit S9) so a future `tracing::error!(?config, …)` can't dump the platform credential straight into structured logs.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `account_strategy` | [Account Strategy](#account-strategy) | No | Not declared |
| `accounts` | Array of [Provider Account](#provider-account) | No | Not declared |
| `active` | `boolean` | No | `true` |
| `api_base` | `string` | No | `""` |
| `api_key` | `string` | No | `""` |
| `api_protocol` | [Pattern Map for Protocol List](#pattern-map-for-protocol-list) | No | Not declared |
| `auto_discover` | `boolean` | No | `false` |
| `class` | [Provider Class](#provider-class) or `null` | No | Not declared |
| `derives` | `string` or `null` | No | `null` |
| `headers` | Map of `string` → [Provider Header Config](#provider-header-config) | No | Not declared |
| `models` | Array of [Provider Model](#provider-model) | No | Not declared |
| `priority` | `integer` or `null` | No | `null` |
| `protocol_endpoints` | Map of `string` → `string` | No | `{}` |
| `rate_limits` | [Pattern Map for Rate Limit](#pattern-map-for-rate-limit) | No | Not declared |
| `tags` | Array of `string` | No | `[]` |
| `timeouts` | [Timeout Config](#timeout-config) | No | Not declared |

- `account_strategy` — How the per-account targets are ordered when `accounts` is set.
- `accounts` — Multiple credentials for this one provider — e.g. two subscriptions to the same upstream. When non-empty, the routing table expands the provider into one routing target per account; `account_strategy` decides their order. Empty = a single-credential provider keyed off the top-level `api_key` (the common case).
- `active` — Whether this provider is active / routable.
- `api_base` — Upstream API base URL.
- `api_key` — Upstream API key (often a `${VAR}` reference).
- `api_protocol` — Glob-prefix `api_protocol` pattern list — each pattern maps to an ordered set of supported wire protocols (the head is the preferred default). Precedence: per-model override &gt; longest matching pattern &gt; host-inferred default. A bare protocol string still parses to a one-element set, so single-protocol providers are unchanged.
- `auto_discover` — When `true` and `models` is empty, discover models from the provider's `/models` endpoint at startup and on reload.
- `class` — Routing-preference class. Set by the public registry merge (or directly in config), then mapped to a numeric rank via `RegistryConfig::provider_priority`. `None` ⇒ unclassed: the provider sorts after every classed one in the auto-cascade (Strategy 3). Plain configs leave this `None`, preserving the alphabetical default order.
- `derives` — Inherit defaults from another provider in this config (acceptance F20 / v0 `derives`). The named provider's `headers`, `api_protocol`, `rate_limits`, `models`, `tags` and `auto_discover` flow into *this* provider's empty fields; explicit fields here win. Resolved by `resolve_derivations` after the config is parsed.
- `headers` — Additional headers applied to every inference request for this provider. A string is shorthand for a static default. The expanded form can opt into forwarding the same inbound header, which overrides the default for that request.
- `models` — Declared model entries. Empty + `auto_discover` triggers discovery.
- `priority` — Explicit routing priority (lower = preferred). When set it overrides the class-derived rank, so an operator can pin one provider ahead of others regardless of class. `None` ⇒ derive the rank from `class`. `format`: `int32`
- `protocol_endpoints` — Optional per-protocol base-URL override, keyed by protocol name (`ApiProtocol::as_str`). When one provider serves different protocols at different paths under a single host — e.g. OpenAI-style under `BASE/v1` and Anthropic Messages under `BASE/anthropic` — give each protocol's base here; protocol-native routing copies the chosen protocol's base onto the routing target. Protocols absent here use `api_base`.
- `rate_limits` — Glob-prefix `rate_limits` pattern list, keyed per matched pattern.
- `tags` — Free-form tags, used by `RoutingPrefs.require_tags` filtering.
- `timeouts` — Per-provider upstream timeout overrides. Each set field layers over the resolved global `UpstreamConfig::timeouts`; unset fields inherit it. Not inherited via `derives`.

### Virtual Model

An explicit virtual-model definition (Strategy 2).

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `endpoints` | Array of [Virtual Endpoint](#virtual-endpoint) | Yes | Not declared |
| `pricing` | [Pricing Config](#pricing-config) or `null` | No | Not declared |

### Registry Config

Runtime public registry integration settings — the top-level `registry:` block in `bitrouter.yaml`.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `enabled` | `boolean` | No | `true` |
| `provider_priority` | Array of [Provider Class](#provider-class) | No | Not declared |
| `url` | `string` | No | `"https://raw.githubusercontent.com/bitrouter/bitrouter/main/dist/registry"` |

- `enabled` — Whether to fetch the registry and merge its BYOK providers into the routing table. Default `true`. Also gated by `inherit_defaults` — either being false disables the merge.
- `provider_priority` — Provider-class priority, highest first. A provider's auto-cascade rank is its class's index here; a per-provider `ProviderConfig::priority` overrides it, and a class absent from this list ranks last. Defaults to `ProviderClass::default_priority`.

### Account Strategy

How a multi-account provider's per-account targets are ordered.

Exactly one of the following shapes:

**`Alternative 1`**

Accounts in declared order — the first is primary; routing drops to the next on a retryable failure (5xx / 429 / timeout) or a payment / credit-exhaustion error. The default.

Accepted value: `"failover"`.

**`Alternative 2`**

Accounts ordered with a process-random rotation so the primary (and therefore the load) spreads evenly across accounts. The remaining accounts still act as failover targets for that request.

Accepted value: `"balance"`.

### Provider Account

One credential within a multi-account provider. An account varies only the credential (and optionally the base URL) — the protocol, model catalog, and rate limits are the provider's.

| Field | Type | Required | Schema default |
| --- | --- | --- | --- |
| `api_base` | `string` | No | `""` |
| `api_key` | `string` | No | `""` |
| `label` | `string` | No | `""` |

- `api_base` — Optional per-account `api_base` override. Empty inherits the provider's `api_base` — set it only for multi-region / multi-org deployments where each account lives on a different host.
- `api_key` — This account's API key (often a `${VAR}` reference).
- `label` — Optional human label, surfaced in the request log so an operator can see which account served a request. Defaults to `account-<n>` (1-based) when empty.

### Pattern Map for Protocol List

Glob-prefix pattern list; each entry is a single-key object mapping a pattern (`*`, `prefix*`, or an exact literal) to its value.

### Virtual Model Strategy

How a `VirtualModel`'s endpoints are ordered into its fallback chain (Strategy 2). Mirrors the typed-enum + serde pattern of `AccountStrategy`. Both strategies build a chain that `execute_with_fallback` walks: a retryable failure (5xx / 408 / 429 / timeout / credit-exhaustion) always advances to the next endpoint — that failover-on-error behaviour is a property of *any* chain and is shared by both. They differ only in the **order** the endpoints take in that chain.

Exactly one of the following shapes:

**`Alternative 1`**

Endpoints are tried in **declared YAML order** — the first is the preferred endpoint, the rest are failover targets reached only when a preceding one fails with a retryable error. Routing preferences (`sort` / `only` / `ignore`) do **not** reorder or filter the chain: the operator's declared priority is authoritative. This is the default and matches the historical (pre-typed-`strategy`) behaviour.

Accepted value: `"priority"`.

**`Alternative 2`**

Endpoints are treated as an unordered candidate set and **re-ordered by the request's `SortOrder`** (the same cascade ordering Strategy-3 auto-cascade applies to providers), and filtered by `only` / `ignore` / `require_tags`. Use this when the endpoints are interchangeable and you want cost/latency-aware (or, today, alphabetical) selection rather than a fixed priority order. `Latency` / `Cost` have no metrics source yet, so they currently fall back to alphabetical-by-provider — the same honest limitation Strategy-3 documents.

Accepted value: `"cascade"`.

### Mcp Upstream Protocol

`mcp.upstream_protocol` — the startup lifecycle and protocol version the gateway uses when dialing upstream MCP servers. `auto` (the default) starts with modern `server/discover` and uses rmcp's classified legacy fallback. `latest` forces the legacy `initialize` path; `2026-07-28` is the explicit spelling of the modern preference.

Exactly one of the following shapes:

**`Alternative 1`**

Prefer `server/discover` and `2026-07-28`, falling back through rmcp's compatibility path when the upstream identifies itself as legacy.

Accepted value: `"auto"`.

**`Alternative 2`**

Use the legacy `initialize` lifecycle with the latest version the MCP SDK treats as current — today `2025-11-25`.

Accepted value: `"latest"`.

**`Alternative 3`**

Use `server/discover` and the modern `2026-07-28` lifecycle. rmcp falls back after its discovery timeout or a correlated JSON-RPC error it classifies as legacy; transport failures, malformed or uncorrelated responses, and modern rejection codes fail the connection. Opting in also lets upstreams answer `tools/call` with MRTR `input_required` or a Tasks `task` handle; neither is a shape this gateway can carry, so both surface as explicit errors (see `docs/MCP_2026_07_28_SPEC.md` D1).

Accepted value: `"2026-07-28"`.
