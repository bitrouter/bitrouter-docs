---
title: Routing Traces
description: Trace routing decisions across your workflow, from the requested model to the serving route and its recorded outcome.
---

See which models served each step of a workflow, how routes changed, and what those choices cost. Routing Traces connects the router's decisions with the requests and upstream attempts that actually ran.

## Follow the workflow trajectory

An agent may inspect files, make changes, call tools, and verify a result across many model requests. Inspect the routing evidence in that execution order, rather than treating each model call as an unrelated event.

For each observable step, compare:

| Question | Evidence to inspect |
| --- | --- |
| What did the caller request? | The model selector and the request's workflow or trace association, when available |
| What did the router select? | The resolved model, provider, and recorded decision evidence |
| What actually executed? | The upstream attempts, retry or fallback transitions, and final serving route |
| What did that choice consume? | Recorded token usage, cost, latency, and execution status |
| What changed between steps? | Model or provider changes and policy identity or context-selection evidence, where recorded |

A selected route and the final serving route can differ after a fallback. Keep the decision, attempted executions, and settled result distinct.

## Start with a request

For a local deployment, inspect recent settled requests:

```bash
bro requests --limit 25
```

[Request receipts](/docs/cli/request-receipts) distinguish the requested selector from the resolved model and serving provider. Match a request to your workflow using the available request identifiers and recorded correlation evidence. Timestamp proximity alone does not establish that two requests belong to the same workflow.

Cloud Activity and `bro cloud requests --limit 25` provide Cloud request records. Receipts summarize settled requests; they are not a complete workflow timeline.

## Inspect routing and upstream attempts

For more detail, configure [OpenTelemetry export](/docs/self-hosting#opentelemetry) and inspect the trace in your OTLP backend. BitRouter exports ingress and routing spans, upstream attempt spans, and settlement metadata. Retry and fallback attempts remain separate hops.

Use the parent-child span relationships and propagated trace context to place router activity alongside the caller's instrumented workflow. Expand a request to compare its routing activity with each attempted model execution, then return to the surrounding workflow to see how later steps proceeded.

Recorded rule matches, candidate constraints, policy identity, or decision evidence can explain a choice when the runtime emits them. An absent explanation is missing evidence; it is not permission to infer a model's private reasoning or an unrecorded decision.

## Understand coverage

<Callout type="info">
Workflow coverage depends on the runtime, correlation evidence, instrumentation, and sampling. Routing an external harness through BitRouter exposes the model requests it sends to the router; it does not automatically expose every tool action, private session event, or internal context change in that harness.
</Callout>

Check the scope of the evidence before drawing conclusions:

- **Request coverage:** which model requests reached this BitRouter instance and were retained or exported?
- **Workflow correlation:** which requests have an established shared workflow or trace association?
- **Attempt coverage:** which upstream attempts and outcomes were recorded?
- **Agent coverage:** which tool and agent events were emitted by the host itself?

Keep unresolved associations and gaps visible. A successful request does not prove task success, and a lower request cost does not prove that the workflow improved.
