BitRouter gives an agent one local model endpoint and a version-controlled
routing policy. The public model is always `@auto`: its strong and economy
tiers may use different providers, but every workflow request still passes
through the same BitRouter daemon.

## Install the CLI

<Tabs items={['macOS / Linux', 'Homebrew', 'npm', 'cargo']}>
<Tab value="macOS / Linux">

```bash
curl --proto '=https' --tlsv1.2 -LsSf \
  https://github.com/bitrouter/bitrouter/releases/latest/download/bitrouter-installer.sh | sh
```

</Tab>
<Tab value="Homebrew">

```bash
brew install bitrouter/tap/bitrouter
```

</Tab>
<Tab value="npm">

```bash
npm install -g bitrouter
```

</Tab>
<Tab value="cargo">

```bash
cargo install bitrouter
```

</Tab>
</Tabs>

## Run guided setup

From the Git repository that contains your agent workflow:

```bash
bitrouter init
```

The wizard walks through four decisions:

1. **Credentials.** Sign in to BitRouter Cloud with OAuth, reuse a provider
   subscription such as Codex, or configure your own provider key.
2. **Harness.** Select an installed coding agent such as Codex or Claude Code.
3. **Workflow optimization.** Opt in if you want BitRouter to measure your
   workflow now. It discovers project-owned eval and benchmark entrypoints,
   asks when more than one is plausible, and asks what observable output means
   success.
4. **`@auto` tiers.** Reuse the current strong/economy routes when they already
   exist. Otherwise, choose the two provider-qualified models explicitly; the
   wizard does not assume a vendor or model family.

The guided optimization path creates a conservative `@auto` strong/economy
ladder. A typical setup can use a Codex subscription for the strong tier and a
BitRouter Cloud OAuth model for the economy tier. Provider credentials remain
in their native stores; they are not copied into `bitrouter.yaml` or an
optimization lock.

<Callout type="info">
Already configured? Run `bitrouter optimize setup` directly. With no workflow
flags it uses the same discovery flow. If discovery is ambiguous or finds
nothing, pass an exact argv with `--workflow-command` and repeated
`--workflow-arg` values. A non-interactive fresh setup must also pass
`--strong` and `--economy`; `bitrouter init --yes --optimize` uses the equivalent
`--optimize-strong` and `--optimize-economy` flags.
</Callout>

### Let an agent drive setup

For an agent runtime that supports Agent Skills:

```bash
npx skills add bitrouter/bitrouter
```

Then ask the agent: *"Set up BitRouter and configure measured `@auto`
optimization for this workflow."* The bundled skill follows the same CLI
contract; there is no separate routing implementation.

## Route through `@auto`

Start the local daemon and launch your coding agent through it:

```bash
bitrouter start
bitrouter launch -a codex
```

`bitrouter launch` supplies the harness-specific routing adapter without
editing the agent's global config. For example, Codex keeps its subscription
authentication while its model requests enter the daemon as `@auto`.

You can call the same preset from any supported wire protocol. A local curl
smoke test is:

```bash
curl http://127.0.0.1:4356/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "@auto",
    "messages": [{"role": "user", "content": "Hello!"}]
  }'
```

| Surface | Local path |
| --- | --- |
| OpenAI Chat Completions | `/v1/chat/completions` |
| OpenAI Responses | `/v1/responses` |
| Anthropic Messages | `/v1/messages` |
| Google Generative Language | `/v1beta/models/{model}:generateContent` |

The daemon translates the inbound protocol to each selected provider's native
protocol. `@auto` is the only stable public preset; `auto` is only its internal
preset and policy key.

## Optimize your workflow

If you did not opt in during `bitrouter init`, start with:

```bash
bitrouter optimize setup
```

Setup creates version-controlled intent, lock, and success-contract files:

- `bitrouter.optimize.yaml` — workflow argv, route ladder, preference, and
  normalized price overrides;
- `bitrouter.optimize.lock.yaml` — resolved evaluator, executable, source, and
  policy digests;
- `bitrouter.eval.md` — the observable quality contract the judge applies.

Review those files like code. If the workflow needs ignored inputs such as
`node_modules`, `.venv`, or generated fixtures, repeat `--workflow-input PATH`
so both variants receive the same frozen input.

Run one controlled comparison:

```bash
bitrouter optimize run --human
bitrouter optimize review --human
```

`run` executes the same frozen workflow once as the active baseline and once
with exactly one eligible route changed from strong to economy. It does not
retry either workflow identity. `review` shows:

- the route key and strong/economy model pair;
- the agentic evaluator's baseline and candidate verdicts;
- normalized showback cost and the percentage delta;
- observed latency, which is reported but does not gate publication;
- the candidate and evidence digests; and
- whether the candidate is publishable.

The agentic evaluator is separate from the workflow model path. By default it
uses a detected Codex or Claude subscription in a fresh ACP session. It judges
only the user-authored success contract; daemon-authored settlement remains
the authority for cost, latency, route attribution, and policy lineage.

If quality passed, normalized cost fell, and the lineage is still current:

```bash
bitrouter optimize publish
```

The first publication asks on a TTY before changing `policy.mode` from
`frozen` to `adaptive`. Headless automation must opt in explicitly with
`--enable-adaptive`. `run` itself never publishes.

After publication, the same `@auto` model sends that request shape to the
economy tier. Run the loop again to consider one more route. Restore a prior
reviewed policy at any time with:

```bash
bitrouter optimize rollback sha256:<policy-digest>
```

<Callout type="warn">
`quality-first`, `balanced`, and `savings-first` control which eligible route
BitRouter evaluates first. They are not fixed quality-loss percentages. This
release still requires an explicit agentic pass and lower normalized cost;
latency is observe-only.
</Callout>

<Callout type="info">
Both the strong and economy workflow tiers always run through a fresh private
BitRouter daemon during optimization. A provider subscription, BitRouter Cloud
OAuth, BYOK, or a local model changes the daemon's outbound provider — never
the workflow's routing boundary.
</Callout>
