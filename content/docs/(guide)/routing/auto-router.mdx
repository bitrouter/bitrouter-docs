Use `bitrouter/auto` when a bound policy should select the model for each request. Connect usable inference sources first, initialize the policy binding, then inspect the serving route and review evidence before publishing policy changes.

[Strategies](/docs/routing/strategies) explains selector resolution, candidate eligibility, and named variants. [Configuration (YAML)](/docs/routing/configuration) covers file discovery, validation, and reload. Automatic model selection remains separate from [Model Fallbacks](/docs/models-routing/model-fallback) after a retryable failure.

## Local and Cloud pricing

Self-hosting the OSS router has no BitRouter fee. Cloud Auto Routing with BYOK costs **$0.01 per million verifiable routing input tokens**; your provider bills inference separately. Flex Inference instead adds a **5% transaction fee** to the supplier’s actual settled charge and includes Cloud Auto Routing without a separate fee. Enterprise terms are custom. See [pricing](/pricing).

## Policy tiers and runtime adequacy

Initialize a binding with usable models for its tiers, then adjust the policy's supported adequacy settings. An unmatched fingerprint uses the conservative default; escalation, cooldown, and exploration settings govern subsequent runtime behavior. Initialize the binding below; [Auditable Policies](/docs/routing/auditable-policies#let-evidence-improve-the-policy) explains adequacy observations and their publication boundary.

Context-view selection has separate runtime rules. The model policy lock does not configure an external harness's history, and this page does not introduce unsupported context-strategy YAML. See [Context Routing](/docs/routing/context-routing).

## Initialize a policy binding

`bitrouter/auto` uses the routing policy bound to the `auto` preset. An explicit logical model id selects that model while retaining eligible provider fallback; a provider-qualified id pins one provider. Automatic selection and failure-driven fallback are separate decisions.

For a local deployment, initialize the policy binding with connected, usable tier models:

```bash
bro policy init auto --preset auto \
  --strong openai/gpt-5.4 \
  --economy moonshotai/kimi-k2.7-code
bro policy check
bro route bitrouter/auto
```

The initializer writes `policy-lock.yaml` and updates `bitrouter.yaml`. The endpoint fails visibly if the required binding is missing. Cloud callers need an `auto` policy available to their active workspace.

Use the selector in an API request or native harness launch:

```bash
bro claude --model bitrouter/auto
bro codex --model bitrouter/auto
```

[Responses API](/docs/usage/responses-api) shows a routed generation request. Inspect the actual serving model with [Request receipts](/docs/cli/request-receipts); a selector preview does not prove which fallback ultimately served the call.

## Override one call

Use an explicit selector when the caller should choose the model for one invocation:

```bash
bro claude --model openai/gpt-5.4
bro codex --model openai:openai/gpt-5.4
```

An explicit logical id retains eligible provider alternatives. A provider-qualified id also pins the provider. See [Virtual Models](/docs/models-routing/virtual-models#model-selector-forms) for selector resolution and named endpoint definitions.

## Verify and apply the policy

```bash
bro config validate -c bitrouter.yaml
bro route bitrouter/auto -c bitrouter.yaml
bro policy check -c bitrouter.yaml
bro requests --limit 25
```

Use `policy check` to inspect the binding used by `bitrouter/auto`. For other selectors and candidate constraints, use [Strategies](/docs/routing/strategies). Route previews do not send inference or establish task quality; settled [Request receipts](/docs/cli/request-receipts) show what actually served a call. Apply configuration changes through [Configuration (YAML)](/docs/routing/configuration#apply-and-review-changes), and publish policy candidates through the [review workflow](/docs/routing/auditable-policies#review-and-publish-a-change).
